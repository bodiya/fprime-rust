# Data Products (Fw/Dp, Svc/DpPorts, Svc/DpManager, Svc/DpWriter, Svc/DpCatalog)

> Analysis of the C++ F Prime implementation (github.com/nasa/fprime) produced to guide this Rust port.
> File paths refer to the C++ tree.

## Overview

The data-product chain: a client component asks DpManager for a buffer (sync `Fw.DpGet` or async `Fw.DpRequest`/`Fw.DpResponse`), fills it as an `Fw::DpContainer` packet, and sends it back on `Fw.DpSend`; DpManager forwards it on `Fw.BufferSend` to DpWriter, which validates the header hash, optionally runs processing ports, computes the data hash, writes the whole packet to a `.fdp` file, notifies `Svc.DpWritten`, and deallocates the buffer. DpCatalog scans configured directories for `.fdp` files, validates each header, builds a priority-sorted red-black-tree catalog, and downlinks products one at a time through `Svc.SendFileRequest`/`SendFileComplete`, persisting transmit state to a state file. The `Fw::DpContainer` 57-byte header, its CRC32 header/data hashes, and the packet layout are already documented in /home/user/fprime-rust/docs/cpp-analysis/utils-misc.md section "Fw::DpContainer (data product packet)" and wire-format section "DpContainer packet" — do not re-derive; reuse those offsets (Header::SIZE=57, HEADER_HASH_OFFSET=57, DATA_OFFSET=61, MIN_PACKET_SIZE=65, packetSize=57+dataSize+8, dataHashOffset=61+dataSize, DpState U8 UNTRANSMITTED=0/PARTIAL=1/TRANSMITTED=2, ProcType U8 mask NONE=0x00/ZLIB_DEFLATE=0x01/ONE=0x02/TWO=0x04, descriptor 0x0005). Config: FwDpIdType=FwIdType=U32, FwDpPriorityType=U32, FwIndexType=PlatformIndexType=I16, FwEnumStoreType=I32, FwSizeStoreType=U16, FwSizeType=U64(unix), DpManagerNumPorts=5, DpWriterNumProcPorts=5, FileNameStringSize=240, DP_MAX_DIRECTORIES=2, DP_MAX_FILES=127, CONTAINER_USER_DATA_SIZE=32, DP_EXT=".fdp", DP_FILENAME_FORMAT="%s/Dp_%08<FwDpIdType>_%08u32_%08u32.fdp" (basedir, id, time seconds, time useconds; %08 zero-padded).

### Fw DpPorts (Fw/Dp/Dp.fpp)

Files: `Fw/Dp/Dp.fpp`

4 ports + 1 enum. `port DpGet(id: FwDpIdType, dataSize: FwSizeType, ref buffer: Fw.Buffer) -> Fw.Success` — synchronous; on return buffer is valid & >= packet size for dataSize if SUCCESS, invalid if FAILURE. `port DpRequest(id: FwDpIdType, dataSize: FwSizeType)` — no return. `port DpResponse(id: FwDpIdType, buffer: Fw.Buffer, status: Fw.Success)`. `port DpSend(id: FwDpIdType, buffer: Fw.Buffer)`. `enum DpState: U8 { UNTRANSMITTED=0, PARTIAL=1, TRANSMITTED=2 } default UNTRANSMITTED`. `enum SendFileStatus: U8 { STATUS_OK=0, STATUS_ERROR=1, STATUS_INVALID=2, STATUS_BUSY=3 }`; `struct SendFileResponse { status: Svc.SendFileStatus, context: U32 }` (serialized 1+4 = 5 bytes BE); `port SendFileRequest(sourceFileName: string size 100, destFileName: string size 100, offset: U32, length: U32) -> Svc.SendFileResponse` (synchronous return); `port SendFileComplete(resp: Svc.SendFileResponse)`. DpCatalog's file names are FileNameString (240) but the request port strings are size 100 — long DP paths are truncated by the port's string type.

### zlib-dependent components (OUT OF SCOPE)

Files: `Svc/DpZLibCompressor/DpZLibCompressor.fpp`, `Svc/DpCompressProc/DpCompressProc.fpp`, `Svc/DpCompressProc/Ports/CompressChunk.fpp`, `Svc/DpCompressProc/Types/CompressionTypes.fpp`

Svc::DpCompressProc (passive) hangs off DpWriter.procBufferSendOut and drives Svc::DpZLibCompressor (passive) via `port CompressChunk(ref buffer: Fw.Buffer, min_compression: FwSizeType, write_offset: FwSizeType) -> Svc.CompressionAlgorithm`; `enum CompressionAlgorithm: U8 { UNCOMPRESSED=0, ZLIB_DEFLATE=1 }`; `dictionary struct CompressionMetadata { algorithm: CompressionAlgorithm }`. DpZLibCompressor calls libz deflateInit/deflate directly. These are NOT portable to zero-dependency Rust and are OUT OF SCOPE. The only coupling to the in-scope components is the ProcType bit mask: DpWriter fans out on bit index (1<<portNum) over 5 procBufferSendOut ports, bit 0 == PROC_TYPE_ZLIB_DEFLATE. With no processing components wired, procTypes is 0x00 and performProcessing is a no-op — the rest of the pipeline is fully functional.

## Wire formats

### DpContainer packet / .fdp file body

ALREADY DOCUMENTED — see /home/user/fprime-rust/docs/cpp-analysis/utils-misc.md, wire-format section "DpContainer packet (data product; also the .fdp file body written by DpWriter)". Summary for cross-check only: [0..2) descriptor U16=0x0005; [2..6) id U32; [6..10) priority U32; [10..21) Fw::Time (timeBase U16, timeContext U8, seconds U32, useconds U32); [21..22) procTypes U8; [22..54) userData 32 raw bytes; [54..55) DpState U8; [55..57) dataSize as FwSizeStoreType U16; [57..61) header CRC32 (standard complemented) over [0..57) BE; [61..61+dataSize) data; [61+dataSize..65+dataSize) data CRC32 BE. DpWriter writes exactly getPacketSize() = 57+dataSize+8 bytes starting at buffer.getData() offset 0 — the file IS the packet, no extra framing, no trailing sidecar.

### .fdp file name

"<baseDir>/Dp_%08<id>_%08<seconds>_%08<useconds>.fdp" — DP_FILENAME_FORMAT from default/config/DpCfg.hpp; id is FwDpIdType (U32) printed with PRI_FwDpIdType, seconds/useconds are U32 (PRIu32); each field zero-padded to a MINIMUM of 8 digits (values >= 10^8 print wider). Produced identically by DpWriter (baseDir = configure()'s dpFileNamePrefix) and by DpCatalog (baseDir = m_directories[dir]); DpCatalog rejects any file whose full path does not equal the canonical name it recomputes from the header (event InvalidFileName id 47). The directory-scan filter additionally requires the path to END with ".fdp".

### DpRecord serialization

Big-endian, field order per DpCatalog.fpp: id FwDpIdType(U32, 4) || tSec U32(4) || tSub U32(4) || priority U32(4) || size U64(8) || blocks U32(4) || state Fw.DpState U8(1). SERIALIZED_SIZE = 29 bytes.

### DpCatalog state file

A flat, unframed sequence of fixed-size records, no header, no CRC, no delimiter. Each record = sizeof(FwIndexType) bytes of the directory index followed by DpRecord::SERIALIZED_SIZE (29) bytes. With default unix config FwIndexType = PlatformIndexType = I16, so record = 2 + 29 = 31 bytes, all big-endian, written via Fw::ExternalSerializeBuffer::serializeFrom. Written two ways: pruneAndWriteStateFile() truncates (OPEN_CREATE + OVERWRITE) and rewrites only the used&&visited entries; appendFileState() opens OPEN_APPEND and appends ONE record per transmitted file (state=TRANSMITTED), so duplicate ids for the same product can accumulate between prunes — getFileState() takes the FIRST match in file order. Reading stops at EOF (size==0), at m_numDpSlots records, or on a short read (StateFileTruncated, keeps what was read).

## Threading / concurrency

DpManager: ACTIVE (own thread + message queue). productGetIn is `sync` — the handler runs on the CALLER component's thread and calls bufferGetOut_out (a guarded BufferManager port) inline, so numSuccessfulAllocations/numFailedAllocations are std::atomic<U32>; the event/telemetry ports it touches must be thread-safe. productRequestIn, productSendIn and schedIn are `async` — dispatched on the DpManager thread; numDataProducts (U32) and numBytes (U64) are plain because only that thread touches them. Rust port: keep the split — atomics (or a mutex-free AtomicU32) for the two allocation counters, plain fields behind the component-thread state for the other two. DpWriter: ACTIVE; bufferSendIn and schedIn are async, so ALL file I/O, hashing, processing fan-out and deallocation happen on the DpWriter thread; no shared mutable state outside that thread (all m_num* counters are plain). procBufferSendOut calls are synchronous invocations into passive components on the DpWriter thread. DpCatalog: ACTIVE; pingIn, fileDone, addToCat and all four commands are async, so the entire catalog (RedBlackTreeSet, state-file array, xmit flags) lives on the single component thread and needs no locking. BUILD_CATALOG blocks that thread for the whole directory scan (documented: \"Will block until complete\"), during which pings are not answered — health-ping timeout must accommodate it. fileOut_out (SendFileRequest) is a synchronous port call returning SendFileResponse on the DpCatalog thread; the completion arrives asynchronously on fileDone. sendNextEntry() recurses one level through fileDone_handler -> sendNextEntry, never deeper, because the actual file transfer is async. shutdown()/configure() are called from the topology thread outside normal operation.

## Porting notes

1) Ports: add to fprime-comp's port-trait set — `DpGet` (sync, returns Fw::Success, buffer as &mut Fw::Buffer out-param), `DpRequest`, `DpResponse`, `DpSend`, `Svc::DpWritten`. Model DpGet's ref-out param the way existing sync ports with out-params are already modeled; the Rust idiom `fn dp_get(&self, id: u32, data_size: u64) -> (Success, Buffer)` is fine as long as the trait boundary stays the same shape as other ports. 2) Reuse the existing `Fw::Buffer`, `Fw::Time`, `Utils::Hash` (CRC32) and `Fw::Success` primitives; DpContainer should be ported into fprime-fw exactly as utils-misc.md item 4 prescribes (a view over the buffer with serialize_header/deserialize_header returning the same SerializeStatus discriminants and assert-on-misuse for setBuffer/shrinkBufferSize). 3) DpManager is the easiest: an active component with two counters as AtomicU32, two plain counters, one throttled event, four `update on change` channels, one command. Port array size 5 must be a const generic or a config constant, not hardcoded. 4) DpWriter: the exact ordered validation pipeline matters for event fidelity — implement it as a `Result`-style early-return chain that mirrors the C++ gate order (invalid -> too-small-for-packet -> header-hash -> deserialize -> too-small-for-data -> processing -> filename -> data hash -> write -> notify), then ALWAYS deallocate if the buffer is valid and bump m_numErrors on any failure. Keep the double `setBuffer` (once before checkHeaderHash, once inside deserializePacketHeader) — the second one resets m_dataSize to 0 before the header is read back, which is required for correctness. 5) DpWriter's `%08` filename formatting: use `format!(\"{}/Dp_{:08}_{:08}_{:08}.fdp\", ...)` and bound it to FileNameString(240) with an overflow -> StringFormatStatus::OVERFLOWED mapping, since DpCatalog compares the recomputed name for byte equality. 6) DpCatalog's RedBlackTreeSet<DpStateEntry,127> can be a `BTreeSet`-shaped fixed-capacity structure or, given DP_MAX_FILES=127 and the port's no-heap rule, a sorted fixed array with binary-search insert/remove — the only externally visible behaviors are: begin() = smallest by compareEntries, find() for duplicate detection, insert() returning Success/Failure on full, remove() asserting success. Implement `Ord` for DpStateEntry EXACTLY as compareEntries (priority, tSec, tSub, id — dir excluded). 7) DpCatalog memory: the C++ MemAllocator call only sizes the DpDstateFileEntry array; in Rust make it a `Box<[DpStateFileEntry]>` of DP_MAX_FILES sized at configure() and keep `m_num_dp_slots` as the derived cap so the shrink-on-short-allocation path is representable (a config knob rather than a real allocator is acceptable). 8) State-file record size is `size_of::<FwIndexType>() + 29`; derive it from the config type alias (I16 by default -> 31), never hardcode. Serialize dir with the FwIndexType serializer so an I32 override still round-trips. 9) Fw::Wait (WAIT=0/NO_WAIT=1) and Svc::SendFileStatus/SendFileResponse must exist before DpCatalog; SendFileRequest is a sync port returning SendFileResponse. 10) Suggested order: DpContainer (fw) -> DpPorts/Dp ports (comp) -> DpManager -> DpWriter -> DpCatalog. DpManager+DpWriter alone give a working end-to-end .fdp write path without needing FileDownlink. 11) Test vectors worth locking: a 65-byte minimum packet (dataSize=0) with both hashes; a packet with nonzero user data and dataSize; the canonical filename for id=1, secs=2, usecs=3 -> \"dir/Dp_00000001_00000002_00000003.fdp\"; a 2-record state file.

## Rust feasibility (safe, zero-dependency std)

Everything in DpManager, DpWriter, DpCatalog, DpPorts and Fw/Dp is portable in safe, zero-dependency std Rust: the only external machinery is CRC-32 (already ported as fprime-utils Hash), file I/O and directory enumeration (Os::File / Os::FileSystem::getFileSize / Os::Directory open/getFileCount/read — fprime-os already covers file and filesystem; if Os::Directory with getFileCount/read/NO_MORE_FILES is not yet present it must be added over std::fs::read_dir, and Os::Directory::Status must include OP_OK and NO_MORE_FILES, plus Os::File::BAD_SIZE and DOESNT_EXIST status discriminants which DpCatalog compares against directly). NOT portable: Svc::DpZLibCompressor calls libz (deflateInit/deflate) and Svc::DpCompressProc exists only to drive it — both are OUT OF SCOPE for a zero-dependency port. Best achievable alternative: port neither component and leave DpWriter's `procBufferSendOut: [5] Fw.BufferSend` fan-out intact as a generic extension point; with nothing connected, procTypes is PROC_TYPE_NONE (0x00), performProcessing is a no-op, and the whole get/fill/send/write/catalog/downlink chain is fully functional and byte-compatible. If compression is ever wanted, the same port contract (`CompressChunk(ref Fw.Buffer, min_compression, write_offset) -> CompressionAlgorithm {UNCOMPRESSED=0, ZLIB_DEFLATE=1}`) can be reimplemented later behind a feature flag with a pure-Rust deflate; the ProcType bit-to-port-index mapping (bit 0 = ZLIB_DEFLATE) must be preserved in DpWriter regardless. Two other minor C++-isms: placement-new in resetStateFileData() (replace with plain assignment of Default::default()) and DpWriter's Os::File RAII close (make it explicit or use Drop).

## Gotchas

- DpManager.productSendIn adds `buffer.getSize()` (the whole Fw::Buffer size from the BufferManager bin) to NumBytes, NOT the DpContainer packet size — the telemetry over-reports whenever the bin is larger than the product. Reproduce as-is.
- DpManager.productRequestIn ALWAYS calls productResponseOut_out even on allocation failure, sending an invalid buffer with status FAILURE. The response goes out on the SAME port index as the request; productSendOut likewise mirrors productSendIn's index. DpManager never touches the container header.
- DpWriter's CLEAR_EVENT_THROTTLE clears 7 of the 8 throttled events — FileNameFormatError (id 5) is declared `throttle 10` but its ThrottleClear is never called. Port the omission.
- DpWriter never closes the file explicitly (relies on Os::File's destructor) and never writes a .CRC32 sidecar — the data hash lives inside the packet itself.
- DpWriter calls container.setBuffer(buffer) TWICE (once before checkHeaderHash, once at the top of deserializePacketHeader). setBuffer resets m_dataSize to 0, which is required before deserializeHeader reads it back; do not "optimize" the second call away.
- DpWriter's processing fan-out is `procTypes & (1<<portNum)` over port indices, so PROC_TYPE_ZLIB_DEFLATE (0x01) maps to procBufferSendOut port 0, ONE (0x02) to port 1, TWO (0x04) to port 2 — ProcType values are bit masks, not port numbers.
- DpCatalog telemetry channels CatalogDps (id 0) and DpsSent (id 1) are declared in the FPP but NEVER written by the implementation. Event CatalogXmitStarted (id 10) and DpDuplicate (id 28) are likewise declared but never emitted. Keep them declared for dictionary compatibility.
- DpCatalog event ids are EXPLICIT with gaps: 0-5, 10-14, 20-32, 34-49. There is no id 6-9 and no id 33. Do not renumber.
- In DpCatalog's FileHdrError for a bad header CRC, the arguments are passed as (exp = computedHash, act = storedHash) — the reverse of what the names suggest. Reproduce the argument order literally.
- DpStateEntry equality/ordering deliberately EXCLUDES `dir`, so the same product id/priority/timestamp in two managed directories is treated as a duplicate (DpFileSkipped) and only the first is cataloged. But getFileState() DOES require dir to match for state-file lookup.
- DpCatalog rejects any .fdp whose full path is not byte-identical to the canonical name recomputed from its own header (InvalidFileName, id 47), and skips any file whose header DpState is already TRANSMITTED (DpFileSkipped, id 45) — both return ProcessFileStatus::FAILED, which continues the scan rather than aborting.
- processFile returns QUIT (stop scanning this directory) only for insert failure and for m_pendingFiles > m_numDpSlots; every other failure is FAILED (skip file, keep going). A directory open/read/getFileCount error aborts the ENTIRE build with EXECUTION_ERROR.
- The catalog RedBlackTreeSet is a fixed-size MEMBER (DP_MAX_FILES=127); the MemAllocator only backs the state-file tracking array. A short allocation reduces m_numDpSlots (and thus the effective catalog cap) but never the tree's capacity.
- CLEAR_CATALOG does not check or clear m_xmitInProgress/m_xmitCmdWait; it only clears the catalog and sets m_catalogBuilt=false. A fileDone arriving afterwards takes the !m_catalogBuilt branch, clears xmit state and answers any waited command with EXECUTION_ERROR.
- STOP_XMIT_CATALOG does not cancel the in-flight FileDownlink transfer; it only clears m_xmitInProgress so the next sendNextEntry() returns immediately. The in-flight file's fileDone still performs full accounting, appends its TRANSMITTED state, and removes it from the catalog.
- START_XMIT_CATALOG arms m_xmitCmdWait BEFORE calling doCatalogXmit so an empty catalog (which completes inside sendNextEntry) still gets a command response; dispatchWaitedResponse self-disarms to prevent duplicate responses. Failure paths clear the arm and respond with the failure directly.
- appendFileState APPENDS one record per transmitted product without deduplication, so the state file can hold multiple records for the same product until the next pruneAndWriteStateFile; getFileState uses the FIRST match in file order.
- The state file has no CRC and no framing — a torn write is only detected as a short trailing record (StateFileTruncated, id 37), and a missing state file is a normal WARNING_LO NoStateFile (id 40) returning OK, not an error.
- DpCatalog's directory scan accepts a file only if ".fdp" is its FINAL suffix (loc + 4 == length); non-matching files are skipped without consuming a catalog slot, and the free-slot check happens before the filename format, so a full catalog breaks out of the file loop mid-directory.
- DpCatalog's SendFileRequest port strings are `string size 100` while its own file names are FileNameString(240) — long DP paths silently truncate at the port boundary.
- addToCat ignores the priority and size arguments carried by the DpWritten port and re-reads everything from the file's own header.
