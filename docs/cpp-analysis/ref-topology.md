# Deployment assembly (TestDeploymentsProject/Ref: topology FPP, generated-topology contract, Main lifecycle, Svc/Subtopologies)

> Analysis of the C++ F Prime implementation (github.com/nasa/fprime) produced to guide this Rust port.
> Source tree analyzed: local clone at commit of 2026-08. File paths refer to that C++ tree.

## Overview

A deployment is an executable assembling component instances into a wired topology. Its inputs: (1) instances.fpp — one `instance` declaration per component giving FPP type, base id, and for active/queued components queue size, and for active ones stack size/priority/cpu; (2) topology.fpp — a `deployment topology` block listing instances plus subtopology instances, "pattern graph specifiers" that auto-wire n:1 services (command, event, telemetry, text event, time, health, param), and named `connections` blocks of explicit `out -> in` port links (with optional port-array indices); (3) RefPackets.fppi — `telemetry packets` grouping channels into numbered packets with an `omit` list; (4) system.fpp `system Ref: Ref` marking the system for dictionary generation. From these, the FPP autocoder emits RefTopologyAc.{hpp,cpp} (not in repo) declaring all instance objects and phase functions: initComponents, setBaseIds, connectComponents, configComponents, regCommands, readParameters, loadParameters, startTasks, stopTasks, freeThreads, tearDownComponents, deinitComponents. Hand-written RefTopology.cpp sequences these plus project-specific configuration; Main.cpp parses CLI args into a project-defined `TopologyState`, installs signal handlers, and runs setup → blocking rate-loop → teardown. Reusable subtopologies (Svc/Subtopologies: CdhCore, ComCcsds/ComFprime/ComCcsdsSdls, FileHandling, DataProducts, DpCompression, FileHandlingCfdp) are self-contained FPP topologies exporting aliased "topology ports", parameterized by a Config module (BASE_ID, QueueSizes, StackSizes, Priorities, CpuAffinities) and configured via inline C++ `phase` snippets instead of hand-written topology code. The deployment composes them with `instance CdhCore.Subtopology` etc. and wires only their exported ports. This defines exactly what a Rust deployment API must express: instance declaration with resources, ID windowing, pattern + explicit wiring, phased lifecycle, and composable subtopologies.

### Topology definition + pattern specifiers (topology.fpp)

Files: `TestDeploymentsProject/Ref/Top/topology.fpp`

`deployment topology Ref { ... }` lists `instance X` for each used instance and `instance CdhCore.Subtopology` (also ComCcsds, FileHandling, DataProducts) to embed subtopologies. Pattern graph specifiers auto-generate fan-in/fan-out wiring for every instance having matching special ports: `command connections instance CdhCore.cmdDisp` (per component: cmdRegOut->cmdDisp.compCmdReg[i], cmdDisp.compCmdSend[i]->cmdIn, cmdResponseOut->cmdDisp.compCmdStat; compCmdSend matched with compCmdReg by index via `match` specifier); `event connections instance CdhCore.events` (logOut->events.LogRecv); `telemetry connections instance CdhCore.tlmSend` (tlmOut->tlmSend.TlmRecv); `text event connections instance CdhCore.textLogger`; `health connections instance CdhCore.$health` (health.PingSend[i]->pingIn, pingOut->health.PingReturn[i], only for instances with PingEntries constants); `param connections instance FileHandling.prmDb`; `time connections instance posixTime` (every timeGetOut->posixTime time port). Explicit graphs: named `connections <Name> { a.port[idx] -> b.port }` blocks; local `enum Ports_RateGroups {rateGroup1,rateGroup2,rateGroup3}` names CycleOut indices. `include "RefPackets.fppi"` pulls packet defs into the topology.

### ID windowing scheme

Files: `Fw/Comp/PassiveComponentBase.hpp`, `Fw/Comp/PassiveComponentBase.cpp`, `docs/user-manual/overview/04-cmd-evt-chn-prm.md`, `Svc/DpCompressProc/DpCompressProc.cpp`

PassiveComponentBase holds `FwIdType m_idBase` (default 0) with setIdBase/getIdBase. Generated topology `setBaseIds()` calls setIdBase(base id) on every instance. All locally-declared command opcodes, event ids, channel ids, parameter ids, and data-product container/record ids are declared relative (SignalGen: opcodes 0..3, event ids 0..8, tlm ids 0..7, record id 0, container id 0); autocoded base classes add getIdBase() when registering/emitting and subtract when dispatching (global id = base id + local id; e.g. DpCompressProc.cpp: `record_id = this->getIdBase() + RecordId::CompressionRecord`). So SG1 Settings opcode = 0x10011000+0, cmdDisp CommandsDispatched channel = 0x01000000+0x0000+0. Uniqueness is guaranteed only by non-overlapping base-id windows; the 0x1000 spacing gives 4096 ids per instance.

## Wire formats

### Base-ID window (dictionary ID space, not a byte stream)

32-bit FwIdType. Documented convention (comment at top of /home/user/fprime/TestDeploymentsProject/Ref/Top/instances.fpp): 0xDSSCCxxx — bits 28-31 D=deployment digit (Ref uses 1 for main-topology instances), bits 20-27 SS=subtopology (00 main; subtopology BASE_IDs instead occupy the D digit: CdhCore 0x01000000, ComCcsds 0x02000000, ComFprime 0x03000000, DataProducts 0x04000000, DpCompression 0x04100000, FileHandling 0x05000000, ComCcsdsSdls 0x06000000, FileHandlingCfdp 0x07000000), bits 12-19 CC=component, bits 0-11 xxx=local command opcode/event id/channel id/param id/product id. Global id = instance base id + locally-declared id (addition performed in autocoded base classes via PassiveComponentBase::getIdBase(); reverse mapping by subtraction on dispatch). Instances are spaced 0x1000 apart within a subtopology window.

### ComQueue configuration table indexing

Svc::ComQueue::QueueConfigurationTable entries[]: indices 0..Ports_ComPacketQueue::NUM_CONSTANTS-1 are Fw::Com packet queues in enum order (ComCcsds: EVENTS=0, TELEMETRY=1; enum is `: U8`), followed by Fw::Buffer queues at NUM_CONSTANTS + Ports_ComBufferQueue value (FILE -> index 2). Defined in the comQueue `phase configComponents` block of /home/user/fprime/Svc/Subtopologies/ComCcsds/ComCcsds.fpp; depths/priorities from ComCcsdsConfig (events 200/0, tlm 500/2, file 100/1; lower priority value = served first).

## Threading / concurrency

Three instance kinds set the model. Passive: no queue/thread; handlers run on caller thread. Queued: message queue but no thread; async ports/commands enqueue, drained only when the owner explicitly calls doDispatch() — in Ref, SignalGen's sync schedIn handler drains on the rate group's thread. Active: queue + own thread; startTasks() calls start(priority, stackSize, cpuAffinity) (defaults Os::Task::TASK_DEFAULT); stopTasks() sends ACTIVE_COMPONENT_EXIT message; freeThreads() joins. Priorities in Ref (higher number = higher priority under the POSIX plugin): blockDrv 47, RG1/2/3 43/42/41, cmdDisp 35, comDriver rx task 34 (hand-started, COMM_PRIORITY enum in RefTopology.cpp), aggregator 30, comQueue 29, health 24, pingRcvr 23, events 23, tlmSend 22, cmdSeq 20, dpDemo 19. Timing: main thread blocks inside linuxTimer.startTimer(TimeInterval(1,0)) which invokes CycleOut each second until quit() flips a mutex-guarded volatile flag (called from signal handler); RateGroupDriver (passive) divides ticks by {1,2,4} with offset 0 and invokes each ActiveRateGroup's async CycleIn, so member schedIn calls execute sequentially on that rate group's thread. Drv::TcpClient owns a separately started receive/reconnect task (SocketComponentHelper::start), stopped+joined by hand in teardown after stopTasks/freeThreads. Cross-thread traffic is exclusively via component queues and guarded ports (e.g. cmdDisp.compCmdReg guarded, TlmChan.TlmRecv guarded).

## Porting notes

A Rust deployment API must express, declaratively: (1) instance definition = component type + base id + optional queue depth (queued/active) + optional stack/priority/cpu (active), with per-instance defaults module; (2) a topology as a set of instances + connection graphs, where a connection is (instance, out-port, index) -> (instance, in-port, index) and port arrays are index-addressed; (3) pattern wiring generators that expand command/event/telemetry/text-event/time/health/param n:1 patterns over all instances exposing the corresponding special ports — implement these as derived wiring passes, keyed on the Fw.Command/Fw.Event/Fw.Channel interface port names (cmdRegOut/cmdIn/cmdResponseOut, logOut/logTextOut, tlmOut) and Svc dispatcher ports (compCmdReg/compCmdSend/compCmdStat with index-matching, LogRecv, TlmRecv, PingSend/PingReturn, prm get/set); (4) ID windowing: a single setIdBase per instance, with all opcodes/event/channel/param/product ids declared component-locally and offset at registration/emission, subtracted at dispatch; (5) the phased lifecycle as an ordered, generated sequence — init(queueDepth), setBaseIds, connect, configConstants/configObjects/configComponents, project config hook, regCommands, readParameters, loadParameters, startTasks, [manual driver tasks] — and teardown strictly as stopTasks, joinTasks, [manual driver stop/join], resource dealloc, tearDownComponents, deinit; model it as a builder producing a Topology object with setup(&TopologyState)/teardown(&TopologyState), TopologyState being a user-defined struct threaded through every phase. (6) Subtopologies: reusable topology modules parameterized by a config struct (BASE_ID + per-instance queue/stack/priority/cpu + tunables), exporting a narrow set of named port aliases; composition = embed + wire exported ports only; replace FPP phase snippets with per-instance config closures registered on lifecycle phases, and replace link-time overrides (memAllocator, fprimeRouter/tlmSend/fatalHandler instance swaps) with generic parameters or trait objects supplied in the config struct. (7) PingEntries WARN/FATAL become per-instance health config (u32 pairs) collected into the health component's table at configComponents time. (8) Keep telemetry-packet sets (id, group, channel refs, omit list) as data consumed by dictionary generation and optionally TlmPacketizer. Rust naturally replaces the global-instance model (file-scope C++ objects in TopologyAc) with an owned struct of instances; preserve deterministic construction order and the constraint that connections are fixed before any task starts.

## Gotchas

- dpDemo's base id is 0x0A10 — it violates the documented 0xDSSCCxxx convention and sits near the bottom of the ID space; faithful port should reproduce it for dictionary compatibility but flag it (windows are only 0x1000 wide elsewhere).
- regCommands() must run AFTER setBaseIds() and configComponents() and BEFORE startTasks(); registration sends absolute opcodes (base+local) to cmdDisp, and cmdDisp.compCmdReg is guarded, not async, so registration happens synchronously pre-threading.
- Queued components have no thread: async commands and async product-recv sit in the queue until the sync schedIn handler calls doDispatch(); dropping that explicit drain makes commands silently never execute.
- The `$` in FPP identifiers ($health, $recv, $send, $time, $type, $priority, $port) is only a keyword-escape; generated names drop it (CdhCore.$health -> C++ CdhCore::health, PingEntries scope CdhCore_health).
- Qualified-name flattening: subtopology instance X in module M is referenced as M::X in C++ and M_X in PingEntries/ConfigObjects/ConfigConstants scopes; Ref's own instances get the deployment prefix in PingEntries (Ref_blockDrv).
- health connections only wire instances that have a PingEntries entry; adding a component with pingIn/pingOut but no WARN/FATAL constants is a build error, and both struct-with-enum and namespace-with-enum forms must be accepted.
- CmdDispatcher seqCmdBuff/seqCmdStatus are matched port arrays: a command source must use the SAME index on both (router and cmdSeq each get one slot); the `match` specifier enforces index pairing for compCmdSend/compCmdReg too.
- ComQueue's buffer-queue indices are offset by Ports_ComPacketQueue::NUM_CONSTANTS — enum count leaks into table indexing (FILE lands at entry 2).
- Every dataOut in the comms chain has a mandatory ownership-return path (dataReturnOut/dataReturnIn) and a comStatus back-propagation path; omitting a return wire leaks buffers — in Rust, model buffer ownership transfer explicitly.
- Both DataProducts.productGetIn (synchronous get) and productRequestIn/productResponseOut (async request) are wired from the same client (SG1, dpDemo) — a port-array input accepts multiple client connections at distinct indices assigned automatically.
- Teardown order is load-bearing: stopTasks before freeThreads (join), all task joins before deallocating cmdSeq buffer or running cleanup phases; comDriver task is stopped/joined by hand because it is driver-owned, not startTasks-owned.
- linuxTimer.startTimer() blocks the calling (main) thread; stop is only reachable from another context (signal handler) — the Rust main loop must not assume a returning start call.
- Rate group divisors {1,0},{2,0},{4,0} are (divisor, offset) pairs positionally matched to CycleOut indices via the Ports_RateGroups enum ordering; contexts array must be sized exactly to the RateGroupMemberOut port count.
- Every telemetry channel in the topology must be either packetized or listed in the packets `omit` block (CommandErrors, CS_CurrentSequence are omitted) — packet-set validation is total, not best-effort.
- Instance config code lives in FPP `phase` string snippets executed inside generated functions with generated scopes (ConfigConstants::/ConfigObjects::<M_instance>); configObjects declarations precede configComponents use (e.g. frameDetector, BufferBins).
- comDriver.configure() and its task start are conditional on hostname!=nullptr && port!=0 — topology must run without comms for testing; a port should keep comms optional.
- Subtopology customization is via file/link substitution, not parameters: fprimeRouter, tlmSend (TlmChan vs TlmPacketizer), fatalHandler, and ComCcsds::Allocation::memAllocator are all swapped by overriding config files — a Rust API needs an explicit generic/injection point for each.
